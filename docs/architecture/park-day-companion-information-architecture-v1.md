# Park Day Companion — ארכיטקטורת מידע (V1)

_גרסה 3 | עודכן: 2026-08-27 לאחר 5 ריאיוני ה-n=1 | סעיף 1 מתוך 4 בשלב התכנון שלפני המסירה ל-Claude Code_

**שינויי גרסה 3:** בלוק `sensitivities` חדש ונפרד מ-`intensity` (סעיף 2.5) · שדות פרופיל תכנוניים חדשים (סעיף 5). המקור: `park-day-companion-research-to-build-deltas.md`.

מטרת המסמך: להגדיר **חוזה נתונים אחד** שכל שאר המוצר (UI, כלי התכנון, דשבורד אדמין, וכל הרחבה עתידית) יישען עליו. אחרי שהוא נסגר, Claude Code לא צריך להמציא שום מבנה בעצמו — רק לממש.

**החלטות שנסגרו בגרסה 2:** Epic Universe בפנים · `dining` לא מוגדר כרגע (רק אטרקציות ובידור) · `gets_wet` בשתי רמות · שיוך ליום דרך רכיב לוח שנה · תמיכת park-hopper (יותר מפארק אחד ביום) · **תשתית דו-כיוונית (RTL+LTR) ו-i18n מהיום הראשון**, גם אם כל התוכן ב-V1 בעברית.

## 0. ארבע החלטות-על שמכתיבות את כל השאר

**החלטה א' — היררכיה בת 5 רמות, לא 3.**
`destination → resort → park → land → experience`
V1 מכיל רק destination אחד (Orlando) ושני resorts (WDW, Universal Orlando), אבל הרמות קיימות מהיום הראשון. עלות: שני שדות מפתח נוספים. תמורה: הרחבה לפריז/טוקיו/קרוזים בעתיד היא הוספת שורות, לא מיגרציה.

**החלטה ב' — ישות תוכן אחת (`experience`), לא שתיים.**
מתקנים והופעות **לא** מקבלים טבלאות נפרדות. הם אותה ישות עם שדה `type`. למה: ~90% מהשדות זהים, וכלי התכנון מתייחס אליהם בדיוק אותו דבר — פריט ברשימת יום. שתי טבלאות = כפילות בכל שאילתה, בכל רכיב UI, ובכל פילטר. שדות ייחודיים לסוג יושבים בתת-אובייקט אחד (`type_data`). זה גם מה שיאפשר להוסיף `dining` כסוג בעתיד בלי לגעת בכלי התכנון — גם אם היום הוחלט לא להגדיר אותו.

**החלטה ג' — הפרדה מבנית בין `facts` ל-`editorial`, לא רק ויזואלית.**
כל שדה תוכן יושב באחד משני בלוקים בלבד. שדה לא יכול להיות בשניהם ולא באמצע. זו ההחלטה החשובה ביותר במסמך, משתי סיבות:

1. היא מיישמת את מנגנון האמון המרכזי מהמחקר ("הפרדה בין עובדה לדעה") ברמת הנתונים, כך שהוא לא תלוי במשמעת של מי שכותב את התוכן.
2. היא **משאירה את שאלת הסדר פתוחה** — בדיוק כפי שהבריף דורש. אם הבלוקים נפרדים, "עובדות קודם" מול "דעה קודם" הוא החלפת סדר של שני קומפוננטים, ואפילו טוגל למשתמש. אם התוכן מעורבב בשדה תיאור אחד — ההחלטה ננעלת בקוד ולא ניתן לשנות אותה בלי לכתוב מחדש את כל התוכן.

**כלל האגודל להכרעה:** אם שני אנשים שונים שראו את המתקן חייבים להסכים על הערך — זו עובדה. אם הם יכולים להתווכח — זו דעה. "3 היפוכים", "משך 4 דקות", "דורש Lightning Lane" = עובדה. "שווה את ההמתנה", "כדאי מוקדם בבוקר", "מומלץ 4/5" = דעה, גם אם היא מבוססת מחקר.

**החלטה ד' (חדשה) — שפה היא מימד של הנתונים, לא תכונה של המוצר.**
אין "גרסה עברית" ו"גרסה אנגלית". יש מוצר אחד עם שכבת locale. כל טקסט — בממשק ובתוכן — עובר דרך אותו מנגנון. פירוט מלא בסעיף 4; ההשלכה המבנית היא שכל שדה טקסט מתורגם הוא **אובייקט לפי locale**, לא שדה עם סיומת `_he`.

### 1.5 `experience` — הישות המרכזית

```jsonc
{

    "opened_year": 1975,
    "duration_minutes": 3,

      "big_drops": false,
      "spinning": false,

    "sensitivities": {                     // ← בלוק נפרד. ראה 2.5. לא נגזר מ-intensity.
      "motion_sickness": "medium",         // none|low|medium|high
      "enclosed_dark": true,               // מקום סגור / חושך / תחושת מלכוד
      "heights": false,
      "loud_sudden": true,

    },

    "height_requirement_cm": 112,          // null אם אין

    "seasonal_window": null

```

**ארבעה כללים שחייבים להישמר:**

1. `facts`, `editorial`, `media`, `sources` הם בלוקים סגורים. שדה חדש נכנס לאחד מהם — אף פעם לא לשורש.
2. `sources` + `author` + `last_reviewed` הם **לא מטא-דאטה טכני — הם פיצ'ר מוצרי**. הם מה שמממש את "שקיפות ההיגיון" שהוגדרה במחקר כתנאי לאמון ב-AI. הם חייבים להיות מוצגים ב-UI, ולכן חייבים להיות חובה בסכמה.
3. שדות נגזרים **לא נשמרים**. "חדש/ישן" נגזר מ-`opened_year`, לא נשמר כ-`is_new`. אחרת התוכן נרקב.
4. `editorial` מפוצל ל-`editorial` (טקסט, לפי locale) ו-`editorial_shared` (דירוגים ו-enums, אחד לכולם). דירוג 4/5 הוא אותו דירוג בעברית ובאנגלית — הכפלה שלו לפי שפה מזמינה סתירה בין הגרסאות.

## 2. הטקסונומיות (מקור אמת יחיד)

כל ה-enums יושבים בקובץ אחד — `apps/web/src/data/taxonomy.ts` — ומיוצאים גם כטיפוסי TypeScript, גם כ-CHECK constraints ב-DB, וגם כמפתחות לתרגום. **הערך ה"גולמי" באנגלית הוא הנתון; התווית בעברית היא תרגום ולא נשמרת בבסיס הנתונים.** לא מרשים ל-Claude Code להמציא ערך enum בשום מקום אחר בקוד — זה המקור הכי נפוץ לבאגים שקטים בפרויקטים כאלה.

### 2.1 סקאלת אינטנסיביות (1-4) — הגדרה מחייבת
| רמה | תווית | הגדרה אובייקטיבית |
|---|---|---|
| 1 | רגוע | ללא תנועה מהירה. מתאים לכל גיל. ללא מגבלת גובה. |
| 2 | קליל | תנועה מתונה, ייתכן חושך/אפקטים. ללא נפילות/היפוכים. |
| 3 | מרגש | מהירות משמעותית או נפילות, ללא היפוכים. מגבלת גובה קיימת. |
| 4 | אקסטרים | היפוכים ו/או נפילות גדולות ו/או G גבוה. |

הסקאלה **פוסקת לפי `intensity_factors`, לא לפי תחושה** — כך שהיא נשארת בצד ה"עובדה". אם אין הסכמה על ערך, זה סימן שהוא באמת שייך ל-`editorial`.

### 2.2 `gets_wet` — שלושה ערכים, שתי רמות הרטבה _(עודכן)_
```
none  |  may_get_wet  |  may_get_soaked
```
| ערך | תווית מוצעת | UI |
|---|---|---|
| `none` | — | לא מוצג כלל |
| `may_get_wet` | עלול להרטיב מעט | טיפה אחת |
| `may_get_soaked` | עלול להרטיב מאוד | שלוש טיפות |

**הניסוח "עלול" הוא חלק מהנתון, לא קישוט.** רמת ההרטבה בפועל תלויה במקום ישיבה, בעונה ובמזל — ולכן שתי רמות מספיקות לקבלת החלטת תכנון (מה ללבוש, מתי ביום) בלי להתחייב לדיוק שאין לנו. זו אותה לוגיקה שמנחה את כל המוצר: לא להתיימר לדיוק שלא נוכל לעמוד בו, כי הבטחה שנשברת בפארק פוגעת באמון יותר מאשר היעדר הפרט מלכתחילה.

### 2.5 `sensitivities` — למה זה בלוק נפרד ולא חלק מאינטנסיביות _(נוסף 27.8, מהריאיונות)_

**הממצא:** שני אימותים בלתי-תלויים (ריאיון #1, ריאיון #4) והקלט של נטע — מתקנים גורמים לחוסר נוחות שאינו נגזר מעוצמה פיזית: קלאוסטרופוביה, חושך, תחושת מלכוד, ובחילה ממתקנים ש**אינם** מסווגים כאינטנסיביים (סימולטורים, תנועה סיבובית איטית).

**ולכן ההפרדה:** `intensity` ו-`intensity_factors` מתארים **עוצמה פיזית**. `sensitivities` מתאר **התאמה אישית**. מתקן יכול להיות `intensity: 1` ובכל זאת בלתי נסבל למי שסובל ממחלת תנועה — ולכן הסקאלה הכללית לא יכולה לשמש כפרוקסי.

```
motion_sickness: none | low | medium | high
enclosed_dark:   bool     // מקום סגור / חושך / תחושת מלכוד
heights:         bool
loud_sudden:     bool
strobe:          bool
```

**שלוש נגזרות מחייבות:**
1. `search_experiences` **חייב** לקבל פילטרים על השדות האלה. בלי זה הממצא לא מגיע למשתמש.
2. אלה שדות `facts` ולא `editorial` — ולכן **T1 בלבד**, לפי כלל הבטיחות. אזהרת בחילה לא נשענת על טיפים קהילתיים.
3. `darkness` ו-`enclosed_space` הועברו לכאן מ-`intensity_factors`, ו-`motion_sickness_risk` הוחלף ב-`motion_sickness`. אין כפילות בין הבלוקים.

### 2.3 שעה מועדפת — enum + שעה ספציפית, בשדה אחד
```
time_preference: { mode: "bucket" | "exact", bucket?: "must_early"|"morning"|"noon"|"afternoon"|"evening", exact?: "14:30" }
```
לא שני שדות נפרדים. שני שדות = מצב לא חוקי שבו שניהם מלאים וסותרים.

## 3. שכבת כלי התכנון

### 3.1 הישויות
```
trip           → user_id, name, destination_id, start_date, end_date, party {adults, kids:[גילאים]}
trip_day       → trip_id, day_index, date, park_ids: string[]  (ריק = יום מנוחה), notes
plan_item      → trip_id, trip_day_id (NULLABLE!), experience_id, ...שדות המשתמש
```

### 3.2 ההחלטה הקריטית: `trip_day_id` הוא nullable
פריט עם `trip_day_id = null` הוא **פריט ב"מאגר המשאלות" של הטיול** — נבחר, אבל עוד לא שובץ ליום.

זה נראה כמו פרט טכני והוא למעשה ההחלטה הארכיטקטונית שמכתיבה את כל ה-UX של הכלי. הוא מפריד את "מה מעניין אותי" מ"מתי אעשה את זה" — שני תהליכים מנטליים שונים לחלוטין. בלעדיו, המשתמש חייבת להחליט על יום ברגע הבחירה, וזה בדיוק ה"תהליך קשיח חד-פעמי" שהבריף אוסר. איתו, כל דפוסי ה-UI האפשריים (גרירה ממאגר ליום, שיבוץ אוטומטי, "שבץ לי את זה מחר") נשארים פתוחים ללא שינוי נתונים.

### 3.3 `park_ids` הוא מערך — תמיכת park-hopper _(חדש)_
יום אינו שייך לפארק אחד. משתמש עם כרטיס park-hopper יעשה שני פארקים ביום, ומשתמש רגיל אחד. לכן `trip_day.park_ids` הוא **מערך מסודר** ולא FK יחיד.

השלכות שנגזרות מזה ישירות, וכדאי ש-Claude Code יכיר אותן מראש:
- **הפריט לא שומר פארק.** הפארק של פריט נגזר תמיד מ-`experience.park_id`. תצוגת היום מקבצת פריטים לפי פארק אוטומטית, בסדר של `park_ids`.
- **מעבר בין פארקים הוא אירוע גלוי.** אם ליום יש שני פארקים, ה-UI צריך לסמן את נקודת המעבר (זמן נסיעה, ולעתים מגבלת שעה של הכרטיס). זה לא מודל נתונים נוסף — זה נגזר מהמערך.
- **אי-התאמה מזהירה, לא חוסמת.** אם משתמש משבץ ליום פריט מפארק שאינו ב-`park_ids`, המערכת מציגה אזהרה רכה ומציעה להוסיף את הפארק ליום — ולא מונעת את הפעולה. חסימה סותרת את עקרון הגמישות; שתיקה מוחלטת סותרת את מניעת החרטה.
- `park_ids` ריק = יום מנוחה/יום ללא פארק. מצב תקין, לא חריגה.

### 3.4 שיוך ליום נעשה דרך לוח שנה, לא הקלדה _(חדש)_
בחירת היום היא תמיד רכיב `date picker` המוגבל לטווח `trip.start_date … trip.end_date`. אין שדה טקסט חופשי לתאריך בשום מקום במוצר.

זה נשמע כמו פרט UI אבל יש לו שתי השלכות מבניות שכדאי לקבע עכשיו:
- **תאריכים נשמרים תמיד כ-`date` בפורמט ISO (`YYYY-MM-DD`), לא כמחרוזת מפורמטת.** הפורמט הוא עניין תצוגה בלבד — וזה קריטי כפול כשיש שתי שפות, כי `20/08/2026` בעברית ו-`August 20, 2026` באנגלית חייבים להיות אותה שורה במסד הנתונים.
- **הלוח מציג את הפארקים של כל יום**, לא רק מספרים. הבחירה היא "יום שלישי, Magic Kingdom", לא "18". זה הופך את הרכיב מקלט טכני לכלי החלטה.

### 3.5 `plan_item` — שדות
| שדה | טיפוס | מקור |
|---|---|---|
| `experience_id` | FK nullable | null = פריט חופשי שהמשתמש המציאה |
| `custom_title` | text | רק לפריט חופשי |
| `priority` | 1-5 | **המשתמש** |
| `time_preference` | object (2.3) | המשתמש |
| `booking_note` | text | המשתמש — טקסט חופשי, **ללא לוגיקה ב-V1** |
| `personal_notes` | text | המשתמש |
| `status` | enum | `wishlist \| planned \| done \| skipped` |
| `sort_order` | int | סדר ידני בתוך היום |
| `overrides` | jsonb | ראה 3.6 |

### 3.6 כלל הברזל: `plan_item` לא מעתיק שום עובדה
אינטנסיביות, סוג כרטיס נדרש, "מרטיב", פארק — כולם **נקראים דרך** `experience_id`, אף פעם לא נשמרים על הפריט. הבריף מציין במפורש שהעמודות האלה "אוטומטיות מהמתקן" — זה בדיוק המימוש. אם נעתיק, כל תיקון תוכן יפסיק להגיע לתוכניות קיימות, ותוך חודשיים יהיו במערכת נתונים סותרים.

היוצא מן הכלל היחיד: דריסה מפורשת של המשתמש נשמרת ב-`overrides: {gets_wet: "may_get_wet"}` — אובייקט נפרד, כך שברור תמיד מה מקורי ומה נדרס.

## 4. שכבת השפה (i18n + דו-כיווניות) _(סעיף חדש)_

המטרה שהוגדרה: **הגרסה האנגלית תהיה עבודת תרגום, לא בנייה מחדש.** זה מושג רק אם ארבעה דברים נכונים מהיום הראשון. אף אחד מהם לא יקר עכשיו, וכולם יקרים מאוד בדיעבד.

### 4.1 אפס מחרוזות בקוד
כל טקסט בממשק הוא מפתח בקובץ תרגום: `t('plan.addToDay')`. אין מחרוזת עברית אחת בתוך קומפוננטה — גם לא "שמור", גם לא הודעת שגיאה, גם לא `aria-label`.
- ספרייה מומלצת: **`i18next` + `react-i18next`**. סטנדרט, קל, ובעיקר מטפל נכון בכללי ריבוי — לעברית יש צורת זוגי שאנגלית לא מכירה, ומימוש ידני של זה תמיד נשבר.
- קבצי התרגום: `apps/web/src/locales/he/*.json`, `apps/web/src/locales/en/*.json`, מפוצלים לפי מרחב (`common`, `plan`, `content`, `admin`).
- **אכיפה:** כלל lint שנכשל על מחרוזת לא-ASCII בתוך JSX. זו השורה שמונעת את הרקבון — בלעדיה, תוך חודש יהיו 200 מחרוזות מוטמעות ואף אחד לא ידע איפה.

### 4.2 טקסט מתורגם בתוכן הוא אובייקט, לא סיומת
```ts
type I18nText = { he?: string; en?: string }   // ולא name_he / name_en
```
שדות עם סיומת שפה נראים פשוטים יותר, אבל כל שפה חדשה היא מיגרציה של כל טבלה. אובייקט = הוספת שפה היא הוספת מפתח.
- **פונקציית קריאה אחת** בכל המוצר: `pick(field, locale)` שנופלת חזרה ל-`he` ואז לשם הקנוני. אף קומפוננטה לא ניגשת ל-`field.he` ישירות.
- **שמות מתקנים אינם תרגום.** `name` הוא תמיד השם הרשמי באנגלית — זה מה שכתוב בשילוט בפארק, וזה מה שהמשתמש תחפש בגוגל. `name_localized.he` הוא תוספת אופציונלית לתצוגה, לא החלפה. גם בגרסה העברית כדאי להציג את השם האנגלי לצד התעתיק.
- **ערכי enum לעולם אינם מתורגמים בנתונים.** במסד שמור `may_get_soaked`; התווית מגיעה מ-`taxonomy` דרך `t()`.

### 4.3 דו-כיווניות: לוגי, לא ימין/שמאל
- `<html dir="rtl|ltr" lang="he|en">` נקבע מה-locale. כל השאר נגזר.
- **רק CSS logical properties**: `margin-inline-start` ולא `margin-left`, `padding-inline`, `inset-inline-start`, `text-align: start`. בפרויקט Tailwind: להשתמש ב-`ms-`/`me-`/`ps-`/`pe-`/`start-`/`end-` ולאסור `ml-`/`mr-`/`left-`/`right-` בכלל lint. זה כל ההבדל בין "החלפת שפה עובדת" לבין "צריך לעבור על 80 קומפוננטות".
- **אייקוני כיוון בלבד מתהפכים** (חצים, "הבא/הקודם", התקדמות). אייקוני תוכן (רכבת הרים, טיפת מים, שעון) לא. כדאי מחלקה ייעודית `.icon-directional` במקום החלטה לכל אייקון.
- **בידוד דו-כיווני הוא חובה, לא עידון.** משפט עברי שמכיל שם אנגלי — "התור ל-Space Mountain ארוך" — נשבר ויזואלית בלי `<bdi>`. במוצר הזה **כל שם מתקן מופיע בתוך טקסט עברי**, אז זה לא מקרה קצה אלא המצב הנפוץ. הפתרון: קומפוננטת `<ExperienceName>` יחידה שעוטפת ב-`<bdi>` — נכתבת פעם אחת, פותרת את זה לתמיד.
- מספרים, שעות ומגבלות גובה נשארים LTR גם בעברית. ה-`<bdi>` מטפל גם בהם.

### 4.4 פורמט הוא פונקציה של locale, לא מחרוזת
כל תאריך, שעה ומספר עוברים דרך `Intl.DateTimeFormat` / `Intl.NumberFormat` עם ה-locale הנוכחי. אין `toLocaleDateString('he-IL')` מקודד קשיח ואין פורמוט ידני. שמירה תמיד ISO (3.4).

### 4.5 Locale ב-URL, לא רק בהעדפה
מסלולים: `/he/parks/magic-kingdom`, `/en/parks/magic-kingdom`.
זה עולה מעט עכשיו ומחזיר שלושה דברים: אפשרות לשתף קישור בשפה מסוימת, אינדוקס נפרד במנועי חיפוש לשני השווקים (מהותי למוצר שהוא בעיקרו תוכן), ו-`hreflang` תקין. העדפת המשתמש ב-`profile.locale` קובעת רק את הפניית ברירת המחדל.

### 4.6 מה **לא** עושים עכשיו
לא מתרגמים שום תוכן לאנגלית, לא בונים ממשק ניהול תרגומים, ולא מוסיפים בורר שפה גלוי אם יש רק שפה אחת. `editorial.en` פשוט חסר — והמוצר מציג במקומו את בלוק העובדות, בלי לשבור. **התשתית מוכנה; התוכן לא נכתב.** זה בדיוק הגבול שמכבד גם את דרישת ההרחבה וגם את עקרון המינימליות.

## 6. איפה הנתונים חיים בפועל

**ההמלצה: Supabase (Postgres + Auth + Storage + RLS), ותוכן שנכתב כקבצי JSON ב-repo ונזרע ל-DB.**

למה לא רק קבצי JSON סטטיים: הבריף דורש חשבונות משתמש, דשבורד אישי ודשבורד אדמין כבר ב-V1. זה מחייב מסד נתונים עם הרשאות. לבנות את זה לבד יקר יותר, פחות בטוח ופחות "חסכוני להרצה" — בניגוד ישיר לעקרון העבודה.

למה בכל זאת JSON ב-repo כמקור התוכן: התוכן נכתב על ידי אדם אחד, נדיר משתנה, ועובר ביקורת. שמירתו כקבצים נותנת היסטוריית שינויים, אפשרות לתקן בבת אחת, ו-diff קריא. דשבורד האדמין עורך את ה-DB; סקריפט seed מסנכרן מהקבצים. שני מסלולי כתיבה לאותו יעד, וזה בסדר כל עוד ה-seed הוא idempotent לפי `id`.

```
apps/web/src/data/
  taxonomy.ts          ← כל ה-enums + מפתחות תרגום. מקור אמת יחיד.
  schema.ts            ← סכמות Zod. כל קובץ תוכן נבדק מולן בזמן build.
  destinations.json / resorts.json / parks.json / lands.json
  experiences/
    wdw-mk.json  wdw-epcot.json  wdw-hs.json  wdw-ak.json
    uor-us.json  uor-ioa.json    uor-epic.json
apps/web/src/locales/
  he/*.json            ← מחרוזות ממשק
  en/*.json            ← שלד ריק ב-V1
scripts/seed.ts        ← מאמת → זורע ל-Supabase
```

**זה החלק שהכי חוסך כאב ראש ל-Claude Code:** סכמת Zod אחת שהיא גם הטיפוס ב-TypeScript, גם ולידציה בזמן build, וגם המסמך. אם שורת תוכן שגויה — ה-build נכשל עם הודעה ברורה, במקום שהאתר יציג `undefined`.

## 8. הצעד הבא — סעיף 2: הפקת התוכן

נטע מרכזת את המידע באקסל ומעבירה. תפקידי: להגיד מה יש, מה חסר, ומה סותר.

**התבנית: `park-day-companion-content-template.xlsx`** — 48 עמודות הממופות 1:1 לסכמה שבמסמך הזה, עם רשימות נפתחות לכל ה-enums, שורת הסבר לכל עמודה, ושורת דוגמה מלאה. ארבעה גיליונות: מקרא והוראות · מתקנים ובידור · אזורים בפארקים · שאלות ופערים.

שתי החלטות בתבנית שאינן קוסמטיות:
- **כותרות צבועות לפי בלוק** (זיהוי / עובדה / דעה / מדיה-ומקורות). ההפרדה עובדה-דעה מיושמת כבר בשלב האיסוף, לא בדיעבד. מי שממלא רואה בכל רגע באיזה צד הוא נמצא.
- **גיליון "שאלות ופערים"** — מקום מוגדר לרשום "לא מצאתי" במקום להשאיר תא ריק שנראה כמו שכחה. ההבחנה בין *חסר* ל*לא קיים* היא בדיוק מה שהופך את דוח הפערים לשימושי.

**מה יקרה כשהקובץ יחזור:**
1. **ולידציה מבנית** — ערכי enum לא חוקיים, סתירות (למשל `intensity: 4` בלי היפוכים ובלי נפילות), כפילויות, אזורים שלא קיימים בגיליון האזורים.
2. **דוח פערים לפי מתקן** — לכל שורה, אילו שדות חובה ריקים ואילו שדות מומלצים חסרים.
3. **דוח כיסוי לפי פארק** — אילו מתקנים קיימים בפארק ואינם בגיליון בכלל. זה החלק שעונה על "לוודא שהכל שם", והוא דורש השוואה מול רשימת המתקנים הרשמית — **לשם כך אצטרך ממך קישור לאתר הרשמי של כל פארק**, גם אם את ממלאת את התוכן לבד.
4. **ייצוא ל-JSON + סכמת Zod** — מרגע שהגיליון נקי, ההמרה היא סקריפט, ומה ש-Claude Code מקבל הוא תוכן מאומת.
